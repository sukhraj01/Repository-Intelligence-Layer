# PyCG — Salis et al. (arXiv 2103.00587v1, ICSE 2021)

Source file: arXiv PDF v1, 12 pages (body 10 pages including the case study, related work and conclusion, references pp.11-12; there is no appendix). arXiv holds only v1, which is the posting of 28 Feb 2021. The extracted text has 12 pages and no blank page (`scripts/check_paper_note.py`). Every page was read, including all three results tables; the reference list was read for the works it names. The ICSE camera-ready may differ from this posting; nothing here was checked against it.

## What it established

- A static, context-insensitive, flow-insensitive call-graph generator for Python 3 that builds an "assignment graph" of identifiers (functions, variables, classes, modules) by fixed-point iteration, then resolves every call to the functions its callee identifier may point to (Sec. III, pp.3-7). Attributes are keyed by the namespace that defines them (not field-based), which the authors say is what raises precision (p.3).
- Handles higher-order functions, closures, nested definitions, multiple inheritance (method resolution order), modules and generators (as thunks evaluated on iteration) (pp.2-7). It does not handle `eval`, `getattr`/`setattr`, methods of built-in types such as `list.append`, and it adds an edge to a function whose source is not available but never follows edges out of it (p.7).
- A micro-benchmark of 112 minimal programs in 16 categories (one execution path each, hand-written JSON call graph, Table I p.7 and Sec. V-A, p.8) and a macro-benchmark of five real packages under 3.5k lines of Python each, with call graphs built by hand (Sec. V-A2, p.8).
- On those two benchmarks PyCG reaches precision about 99.2% and recall about 69.9% on average over the five macro packages, against Pyan and Depends (Table IV, p.9). It also gives time and memory on the same five packages (Table V, p.10) and a dependency-impact case study (Sec. V-E, pp.10-11).

## What it did not establish

- No ground truth for any repository larger than 3.5k lines of Python; the macro ground truth is one person's reading of the source (Sec. V-A2, p.8). The authors checked it by running the three tools and finding 90 missing edges out of 2,506 (p.9), which means the checking was done with the same tools it then scores.
- No dynamic (execution-based) ground truth. Related work says dynamic approaches see one execution path (p.10), and PyCG is never compared with an execution trace.
- The text never states the rule by which a generated edge "matches" a ground-truth edge. Edges are caller-to-callee pairs in JSON; names are fully qualified (module, class, function) per the Figure 2 graphs (p.3), but how external callees, built-in callees and calls from a module namespace are matched is not described (not found).
- No confidence interval, seed or run-to-run variation (the analysis is deterministic; only the timing is averaged over 20 runs, p.10).
- No measurement on projects with their dependencies analysed (PyCG analyses modules inside the package namespace only, Sec. IV, p.8).

## Method details we need (how precision and recall are defined and measured for Python)

- **Call graph.** A map from caller function to a set of callee functions (Algorithm 1, p.7). Callers include the module namespace (a call at module level has the module as caller; Depends misses these, p.9). Edges are context-insensitive and deduplicated.
- **Precision / recall (macro).** "Precision measures the percentage of valid generated calls over the total number of generated calls. Recall measures the percentage of valid generated calls over the total number of calls" (Sec. V-C, p.9). So both are edge-set ratios against the hand-built graph; there is no per-call-site or per-caller normalisation.
- **Complete / sound (micro).** A call graph is complete when it has no false-positive edge and sound when it has no false-negative edge, scored per program as yes or no (p.9).
- **Ground truth.** Micro: hand-written, one execution path per program, no loops or conditionals (p.8). Macro: manual, by the first author, projects chosen under 3.5k lines "so that we could minimize human errors" (p.9).
- **Scope of the edges.** External callees are in the ground truth: the face_classification package "mostly depends on functions declared in external packages", which the authors give as the reason Pyan has 7.6% recall on it (p.9). In-repo-only precision or recall is therefore not what this paper reports.
- **Benchmark.** The micro-suite is released (artifact DOI in Sec. I, p.2); it was extended by the Jarvis paper (`jarvis-2305.05949.md`).
- **Environment.** Debian 9, 16 CPUs, 16 GB (p.8).

## Relation to RQ1 / RQ2 / RQ3

- RQ1: this is the origin of the "edge recovery" idea. It reports 69.9% recall on five small scripts-and-tools packages with hand-built truth and external edges included; the master document's expectation of 70-85% edge recovery (`docs/05_structural_signals.md`) sits at the top of that one number, which was not measured on library-style repositories such as the twelve Verified repositories. The two later Python studies (`jarvis-2305.05949.md`, `dypybench-2403.00539.md`) measure different quantities on different ground truths, so no single "expected recovery" exists in the literature read so far.
- RQ2: none.
- RQ3: none.
- ADR-012 input (no choice made here): the paper's definition is edge-set precision/recall against a manually written graph, external callees included, module-level callers included.

## Discrepancies

- With the Jarvis paper: Jarvis re-runs PyCG on its own benchmark and obtains average recall 0.76 on exhaustive application analysis (`jarvis-2305.05949.md` Table V), not 69.9%; the benchmarks and ground truths differ.
- With DyPyBench: against dynamic call graphs on 39 projects, only 49% of observed edges are in PyCG's graph (`dypybench-2403.00539.md`); the dynamic edges include built-in callees, which PyCG does not resolve (this paper p.7 says as much).
- Internal: the abstract says recall "~69.9%" and the introduction p.2 repeats it; Table IV's recall column averages to 69.9 (checked by reading the raster). No inconsistency.
