# Sun et al. 2022 — On the Importance of Building High-quality Training Datasets for Neural Code Search (arXiv 2202.06649v1, ICSE 2022)

Source file: arXiv PDF v1, 12 pages (body 9 pages, references pp.9-12; there is no appendix). arXiv holds only v1. The extracted text has 12 pages and no blank page. Every page was read, including all eight tables; the reference list was read for the works it names.

## What it established

- Query noise in a comment-derived code-search training set: for the Java training split of CodeSearchNet (394,471 comment-code pairs, first sentence of each comment as the query) the authors count text features that real user queries do not have (HTML tags, parentheses, Javadoc tags, URLs, non-English text, punctuation-only, questions, comments of two words or fewer) in 33.1% of the queries (Figure 1, p.2).
- A two-stage cleaning framework (NLQF): (1) eight syntactic rules, each either removing the offending part or discarding the pair (Sec. 3.1, p.3); (2) a model-based filter that trains a variational auto-encoder on a "bootstrap query corpus" of Stack Overflow question titles and drops comments with high reconstruction loss, with the cut point chosen by a two-component Gaussian mixture on the loss (Sec. 3.2, pp.4-5).
- Training two older neural code-search models (DeepCS and CARLCS) on the filtered Java data gives higher MRR and Answered@k than training on all data and than training on a same-size random subset, on three human-labelled Java evaluation sets (Table 2, p.7).
- Both stages help in an ablation (Table 3, p.8), the mixture-model cut point beats K-means and fixed percentiles (Table 5, p.10), and manual rating by two annotators shows the rejected data scores far lower than the retained data (Table 4, p.9).
- Released artifacts: a Python library and a cleaned dataset of 1,048,519 pairs built from 2,475,692 raw pairs (Sec. 6, pp.9-10).

## What it did not establish

- Nothing about positives that are wrong for a query: the filter scores how natural the query text looks, not whether the paired code is the right answer. This is a different quantity from SweRank's K-rank (`swerank-2505.07849.md`).
- No weighting or curriculum arm and no comparison with one; the only alternatives to the model filter are the rule filter, K-means and fixed percentiles of the same loss ranking (Tables 3 and 5).
- No matched-optimisation comparison: the filtered runs use 192,031 pairs against 394,471 and train for half the hours (4 h against 8 h; Table 2, p.7), with the same 100-epoch limit for both, so the filtered runs take fewer optimiser steps. The size-matched random subset is the only budget-style control and it is worse than the full set.
- Java only (Sec. 4.1, p.5 and threats, p.9); two models; no issue-localization data; no agent.
- Evaluation sets are small: 434, 52 and 287 queries (Sec. 4.1.2, p.6). Medians over five runs are reported; no interval or test is given (Sec. 5, p.7).
- The authors' own caveat that the retained data is still noisy: 59.2% of the retained pairs score 0 in manual rating (Table 4, p.9).

## Method details we need

- **Rule filter** (Sec. 3.1, p.3): rules were derived from a manual inspection of a 1% sample (3,949 comments, p.4); each rule must target one pattern, be conservative, and not be a subset of another. Parentheses and HTML tags are stripped, the other six rules reject the pair.
- **Semantic filter** (Sec. 3.2, pp.4-5): bidirectional GRU encoder and decoder VAE with a Gaussian latent; loss is reconstruction cross-entropy plus KL; the anomaly score is the reconstruction loss of a comment; two-component Gaussian mixture fitted by expectation-maximisation splits the scores. Keeps the lower-loss group.
- **Models and metrics** (Sec. 4, pp.5-7): DeepCS (siamese) and CARLCS (interaction-based) with recommended hyper-parameters except 100 epochs for DeepCS; Answered@k and MRR; each evaluation query is scored against 1,000 candidates (the ground truth plus 999 distractors) in all three sets, built by the authors for the two larger-corpus sets (Sec. 4.1.2, p.6).
- **Controlled set**: a random subset of the training data of the same size as the filtered set (p.7).
- **Evaluation data never filtered**; annotators were hired for manual rating on a 0-2 scale (p.8).
- **Hardware and seeds**: not stated beyond "five independent runs" (p.7).

## Relation to RQ1 / RQ2 / RQ3

- RQ1: none.
- RQ2: the earliest of the three works the master document cites as precedent for "filtering". It is a query-quality filter for comment-derived data with a model-based score, not a positive-correctness filter; it never uses a pretrained retriever as the scorer. It supports the claim that removing noisy queries can raise retrieval metrics on an older architecture, with half the data and half the time, but it did not match optimisation steps.
- RQ3: none; there is no agent and no localization task.

## Discrepancies

- With the master document (`docs/03_literature_map.md`, `docs/02_research_questions.md`): "+19.2% MRR, +21.3% Answer@1" is correct, but it is a relative gain, for DeepCS only, averaged over three small Java evaluation sets, against the unfiltered set, medians of five runs. The same table shows CARLCS +38.6% MRR. The literature-map entry "Over a third of queries noisy" is the abstract's wording; Figure 1 gives 33.1%, which is just under one third.
- Internal: Table 4 lists 161,277 pairs discarded by the rules in total (the per-rule counts overlap), while Table 3 and Table 5 give 285,372 pairs after the rule filter, which implies 109,099 removed; and the model filter is listed as discarding 93,457 pairs although 285,372 minus 192,031 is 93,341. The text does not reconcile these.
