\section{Problem and contribution}

Coding agents work inside a fixed context window while a real repository is far larger, so something must decide which code the agent reads.
The \emph{Repository Intelligence Layer} (RIL) is a repository-level retrieval layer for coding agents: given an issue, it returns a small ranked set of Python code units that fit a token budget.
It combines a function-level index, lexical (BM25), dense and structural (typed code graph) signals, rank fusion and context assembly, and it is the apparatus, not the contribution.
The contribution is a frozen, controlled evaluation: retrievers that differ only in how their training pairs are handled, one fixed agent, and a measurement of whether the difference survives to the resolved rate.
\textbf{RQ1} asks which retrieval signals matter, with latency per stage; \textbf{RQ2} how supervision of the retriever affects retrieval under \emph{matched optimization budgets}; \textbf{RQ3} whether retrieval changes a coding agent's resolved rate.
The scope is Python only, and the contribution is an empirical comparison, not an intervention.

\section{Method}

\paragraph{Retrieval ladder (RQ1).} Dense retrieval (CodeRankEmbed) is the base; BM25 is added by reciprocal rank fusion (RRF), then same-file expansion, then typed graph expansion, which is read against a size-matched same-file control.
Queries are those of a repository-level retrieval benchmark: Level~2 (L2) localizes the code an issue's fix edits and Level~3 (L3) asks for broader context. nDCG@10 rewards placing relevant units early and Recall@100 asks whether they are reachable at all.
All settings were chosen on development repositories only, so the ladder is exploratory.

\paragraph{Training arms (RQ2).} Training pairs are mined from pull requests (the issue is the query, the edited functions are the positives) with no retriever in the loop and audited against held-out repositories.
\textsc{Raw} uses every pair; \textsc{Filter} drops a pair whose positive a separately pretrained BM25 teacher ranks below $K=20$ (SweRank's K-rank); \textsc{Weight} down-weights by the same rank; \textsc{Curriculum} orders pairs easy to hard; a random subsample of \textsc{Raw} of the filtered size is the control. % docs/RQ2_PROTOCOL.md section 3
Every arm trains the same encoder for the same 100 optimizer updates at three seeds, the retrieval stack is frozen across arms, and the retained models are scored once on eight evaluation repositories and on the executable subset. % E-RQ2-FINAL docs/RQ2_PROTOCOL.md section 3
Two contrasts are confirmatory (\textsc{Filter} against \textsc{Raw} and against the subsample); everything else is exploratory.
The decision interval is a cluster-robust $t$ interval inside a Holm step-down, adopted before any final row existed (DEV-040).

\paragraph{Agent evaluation (RQ3).} A fixed one-shot repair scaffold gives one hosted model the issue and the assembled context (8,000 tokens) at temperature 0; it answers with search-and-replace blocks that are applied and graded by running the tests. % docs/RQ3_PILOT.md D113 E-RQ3-AGENT
The confirmatory set is 327 instances: the executable subset of 377 of the 500 instances of a human-validated benchmark (the reference patch passes every named test in two agreeing runs), less a slice of 50 used to choose the model. % E-RQ3-EXEC results/rq3_exec/repo_table.csv docs/RQ3_PILOT.md
The pre-registered analysis has one primary contrast, \textsc{Raw} against the untrained retriever, a paired bootstrap and a sign-flip test, with three adjacent repeats per arm. % E-RQ3-DRIVER docs/RQ3_PILOT.md D113

Table~\ref{tab:short_rq3} gives the arms. The primary contrast, \textsc{Raw} against the untrained retriever, is $+2.45$ points (interval $-$0.82 to $+5.91$, sign-flip $p=0.177$) and is not distinguishable from zero. % E-RQ3-AGENT results/rq3_driver/remaining_arms/rq3_results_contrasts.csv
The other arms do not separate either.
The design could detect only about 7 to 9 points at the measured rate of 40\%, so this is a null with that bound, not evidence of no effect. % E-RQ3-RUN-AGREEMENT results/rq3_driver/rq3_power_measured_agreement_mdd.csv
The exploratory oracle arm, stated before its run, puts the files that the gold patch modifies first in the context; it resolved 45.11\%, $+5.15$ points over the untrained arm (interval $+0.61$ to $+9.73$, unadjusted $p=0.035$, one of eight comparisons), an estimate below the 7.1 to 7.9 points it could detect and so probably inflated. % E-RQ3-ORACLE results/rq3_oracle/rq3_oracle_contrasts.csv
The exploratory floor arm gave the model the issue text and an empty context and resolved 16.91\% of the 272 instances it reached, not near zero as expected, and 25.00 points below the untrained arm on the same instances (interval 19.36 to 30.51). % E-RQ3-FLOOR results/rq3_floor/pooled/rq3_floor_contrasts.csv
Part of every resolved rate may therefore reflect prior knowledge of the repositories, which the data cannot separate from information in the issue text. % E-RQ3-FLOOR docs/experiments/B.md
The plain reading is a null at this power: retrieved context matters a great deal (floor against untrained), while the supervision variants do not separate.
The stored runs say why: in 63 to 68\% of failed runs every file the gold patch modifies was in the context, and with every gold file present the arms resolve 48 to 51\% against 3 to 12\% with none. % E-RQ3-BREAKDOWN results/rq3_breakdown/breakdown.csv
The trained retrievers bring every gold file into the context for only 5 to 7 more of the 327 instances, worth about one point of resolved rate at the untrained arm's per-class rates, so the failures lie mostly in the repair step. % E-RQ3-BREAKDOWN results/rq3_breakdown/summary.json
One attempt uses 12,584 to 13,389 tokens (about one US cent), the 8,000-token context is 0.15\% of django's Python code, and on the floor's 272 instances it covers 83\% of the distance from no context to the oracle arm. % E-RQ3-BREAKDOWN results/rq3_breakdown/attempt_cost.csv results/rq3_breakdown/repo_python_tokens.csv results/rq3_breakdown/summary.json

\section{Limitations}

The graded runs use one hosted model from one provider, one-shot repair with no candidate selection and no search of the repository by the model (so cost against an agent's own exploration is not measured), and each trained arm is one model of one training seed. % E-RQ3-AGENT docs/experiments/B.md
The output limit of 4,096 tokens was reached by 13.7 to 15.5\% of calls in every arm, so some edits may be cut off, equally for every arm. % E-RQ3-AGENT docs/experiments/B.md
The benchmark's repositories are public and the exposure of the model was not measured, which the floor arm makes visible. % E-RQ3-FLOOR docs/experiments/B.md
The floor arm covers 272 of the 327 instances (the 55 not run are all sympy, and 73\% of those run are django), and the executable subset is skewed toward one project. % E-RQ3-FLOOR results/rq3_floor/replay_all/rq3_floor_replay_by_repo.csv
Adjacent repeats are not independent runs, and absolute resolved rates are not statements of agent capability.

\paragraph{What the evidence supports.} Retrieval itself matters: with the same model and repair stage, the retrieved context resolves 41.91\% of the floor's 272 instances against 16.91\% with none. % E-RQ3-FLOOR results/rq3_floor/pooled/rq3_floor_contrasts.csv
Under matched budgets and one fixed retrieval stack, filtering mined pull-request pairs did not separate from raw pairs or a size-matched subsample in retrieval or in resolved rate, a null with its stated bound for Python, one model and one-shot repair, and not evidence that supervision has no effect.
